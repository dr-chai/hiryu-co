> 六大範疇：購物車持久化／結帳 flow／產品圖／Core Web Vitals／SEO／Analytics
> 格式：**技巧名 → 適用場景 → 點做 → 代碼骨架 → 踩坑**

## 1. 購物車持久化（zustand persist）

### 1.1 `skipHydration` + 手動 rehydrate 閘門（防 SSR/CSR mismatch）

**適用場景**：persist 讀 localStorage 令 client 首次 render 同 server HTML 唔同，觸發 hydration mismatch。

**點做**：server 永遠用 default state render；`skipHydration: true` 停咗自動 rehydrate，喺 client `useEffect` 先 `rehydrate()`，並用 `hydrated` flag 閘住會依賴持久化狀態嘅 UI。

```ts
// store/cart.ts
import { create } from 'zustand'
import { persist, createJSONStorage } from 'zustand/middleware'

export const useCartStore = create(
  persist(
    (set, get) => ({
      items: [] as CartItem[],
      add: (item) => set({ items: upsert(get().items, item) }),
      remove: (id) => set({ items: get().items.filter(i => i.id !== id) }),
    }),
    {
      name: 'hiryu-cart',
      storage: createJSONStorage(() => localStorage),
      skipHydration: true,           // 唔好喺 SSR render 時讀 storage
      partialize: (s) => ({ items: s.items }), // 只 persist 需要嘅 field
      version: 1,
    }
  )
)
```

```tsx
// components/CartHydrationGate.tsx
'use client'
import { useEffect, useState } from 'react'
import { useCartStore } from '@/store/cart'

export function CartHydrationGate({ children }: { children: React.ReactNode }) {
  const [ready, setReady] = useState(false)
  useEffect(() => {
    useCartStore.persist.rehydrate()
    setReady(true)
  }, [])
  if (!ready) return null          // 或 render skeleton，避免 flash
  return children
}
```

**踩坑**：① 依賴 cart 數量嘅 badge／價格一定要喺 gate 內，否則首屏 flash 或 mismatch；② 唔好喺 Server Component 讀 zustand persisted 值；③ 需要 SSR 一致輸出時改用 cookie（server 可讀）做 initial source of truth。

### 1.2 `version` + `migrate` + `partialize` 防 stale

**適用場景**：產品 schema 改版（加欄位、改名、改型別），舊 localStorage 資料會撞新 code 或 silent break。

**點做**：`version` 做 schema 版本號，`migrate(persistedState, version)` 升版遷移；`partialize` 只存真正需要嘅 field（排除 transient/不可序列化值）。

```ts
{
  version: 2,
  partialize: (s) => ({ items: s.items }),
  migrate: (persisted: any, version) => {
    if (version === 1) {
      return { items: (persisted.items ?? []).map(i => ({ ...i, variantId: null })) }
    }
    return persisted as any
  },
}
```

**踩坑**：① zustand v5 起 storage 只喺真正 state change 時先寫，`migrate` 要處理 storage 完全空白嘅 case；② `migrate` 成功後會用新版號寫返 storage，唔會重複跑；③ `merge` 係 hydration 時合併持久化 state 同初始 state 嘅位置，預設 shallow merge。

### 1.3 多 tab 同步：BroadcastChannel（優先）／`storage` event

**適用場景**：用戶開兩個 tab，一個 tab 加購物車，另一個 tab 要即時反映。

**點做**：localStorage 做 durable backup，BroadcastChannel 做即時 message bus；收到 `CART_UPDATED` 先 `setItems`，唔好再 broadcast 返出去（防 feedback loop）；unmount 時 `channel.close()`。

```tsx
'use client'
const CHANNEL = 'hiryu-cart-sync'

export function CartSyncBridge() {
  useEffect(() => {
    const ch = new BroadcastChannel(CHANNEL)
    ch.onmessage = (e) => {
      if (e.data?.type === 'CART_UPDATED') useCartStore.setState({ items: e.data.items })
    }
    // 本地變更 → 廣播（用一個常駐 channel instance，唔好每次 subscribe 都 new）
    const unsub = useCartStore.subscribe((s) => {
      ch.postMessage({ type: 'CART_UPDATED', items: s.items })
    })
    return () => { unsub(); ch.close() }
  }, [])
  return null
}
```

**踩坑**：① 每次 callback 都 `new BroadcastChannel` 係反模式——一個 tab 一個常駐 instance 重用；② `storage` event 只喺「另一個 tab 寫 localStorage」先觸發，唔會喺同 tab 觸發；③ 用 `setState` 直接套用嚟避免同自己廣播嘅訊息 loop。

### 1.4 cart id + server sync（guest merge 成真源）

**適用場景**：要上真結帳，cart 唔可以只靠 localStorage；guest 登入時要 merge 去 user cart。

**點做**：server 為 guest 建一個 opaque `cart_id`，client 只存 token（cookie / localStorage）；login 時帶住 guest `cart_id` + auth token 調 server merge endpoint；server 做 quantity 加總 + dedupe + 冪等 merge，之後刪 guest cart。

```
cart_id         → 不透明 server cart 識別
anonymous_id    → guest 關聯 token（cookie）
user_id         → 登入後 owner
```

**踩坑**：① merge 要冪等（重複 login 唔可以重複加 item）；② 客 cart 嘅 price/promotion 快照要同 user cart 重新計算，唔好盲 copy；③ 結帳時以 server cart 做唯一真源，localStorage 只係 UX 快取。

## 2. 結帳 flow（Server Actions + Stripe）

### 2.1 雙層冪等：自家 dedupe lock + Stripe `idempotencyKey`

**適用場景**：雙擊「付款」／server action retry 會開兩張單、收兩次錢。

**點做**：每個「用戶意圖」一個穩定 key（唔係每次 retry 都 random UUID）；server action 先用 Redis/DB lock 做 dedupe，再帶 Stripe `idempotencyKey` 建 session。Stripe key 24 小時內有效，重複 key 回傳原結果。

```ts
'use server'
export async function createCheckoutSession(cartHash: string, userId?: string) {
  const idempotencyKey = `checkout:${userId ?? 'guest'}:${cartHash}`
  const session = await stripe.checkout.sessions.create(
    {
      mode: 'payment',
      line_items: items.map(i => ({ price: i.priceId, quantity: i.qty })),
      success_url: `${BASE}/success?session_id={CHECKOUT_SESSION_ID}`,
      cancel_url: `${BASE}/cancel`,
    },
    { idempotencyKey }
  )
  return { url: session.url }
}
```

**踩坑**：① key 要代表「一次結帳意圖」，用 `checkout:${userId}:${cartHash}`，唔好每次 `crypto.randomUUID()`；② 全新 cart／重新購買先可以換新 key；③ 所有 Stripe POST 都支援 idempotency key，GET/DELETE 無效。

### 2.2 庫存 race condition：atomic decrement / reservation

**適用場景**：9 件選物有庫存，兩個用戶同時買最後一件會 oversell（TOCTOU：先 check 後寫）。

**點做**：把最後一道「夠唔夠庫存」檢查放落 DB transaction，用 guarded update（`UPDATE ... SET stock = stock - n WHERE id = ? AND stock >= n`）或 `SELECT ... FOR UPDATE` 鎖 row；或 checkout 開始先 reserve、付款成功先扣實數。

```sql
-- Postgres：atomic guarded decrement，affected rows = 0 即庫存不足
UPDATE products
SET stock = stock - $1
WHERE id = $2 AND stock >= $1
RETURNING id;
```

```ts
// Prisma + transaction（悲觀鎖 / atomic update）
await tx.product.updateMany({
  where: { id, stock: { gte: qty } },
  data: { stock: { decrement: qty } },
})
// result.count === 0 → 返回「已售罄」，fail fast
```

**踩坑**：① 唔好喺 application 層先 SELECT 檢查再 UPDATE（中間有 race window）；② 付款成功先扣實數，訂單建立先 reservation（避免棄單鎖死庫存）；③ 高併發用 Redis `DECR`（原子）做計數，DB 做最終結算。

### 2.3 webhook 先過戶（唔靠 success page 判成功）+ event 冪等

**適用場景**：Stripe webhook 會重複投遞，同一 event 唔可以出兩張單。

**點做**：用 `checkout.session.completed` 標記付款成功；webhook handler 存 `event.id` 做 primary key（`INSERT ... ON CONFLICT DO NOTHING`）去重。

```ts
export async function POST(req: Request) {
  const sig = req.headers.get('stripe-signature')!
  const event = stripe.webhooks.constructEvent(await req.text(), sig, STRIPE_WEBHOOK_SECRET)
  // dedupe: event.id 唯一約束
  await db.event.create({ data: { id: event.id } })   // 衝突即已處理，return 200
  if (event.type === 'checkout.session.completed') {
    await fulfillOrder(event.data.object)
  }
  return new Response(null, { status: 200 })
}
```

**踩坑**：① webhook 一定要簽名驗證（`constructEvent`）；② handler 要冪等（同 event 重複收到要 no-op）；③ 失敗要回非 2xx 令 Stripe 重試，但要配 dedupe 先安全。

### 2.4 錯誤處理：`useActionState` 回傳結構化錯誤 vs `error.tsx` throw

**適用場景**：Zod 驗證失敗／付款被拒等「預期錯誤」要顯示喺表單，唔好 crash 成個 page。

**點做**：action 內 Zod `safeParse`，驗證失敗 **return** `fieldErrors`；只有「意外錯誤」（DB 掛、bug）先 **throw**，由 `error.tsx` boundary 接。client 用 `useActionState` 接 state。

```ts
'use server'
export async function checkout(prev: State, formData: FormData): Promise<State> {
  const parsed = schema.safeParse({ /* ... */ })
  if (!parsed.success) return { fieldErrors: parsed.error.flatten().fieldErrors }
  try {
    await createOrder(parsed.data)
    return { ok: true }
  } catch {
    console.error('[checkout]', /* log 內部細節 */)
    return { message: '系統暫時故障，請重試' }   // 唔好漏 stack trace 俾 client
  }
}
```

**踩坑**：① 預期錯誤 = return value，意外錯誤 = throw，兩者唔好撈亂；② 內部細節只記 server log，client 回 generic message；③ `error.tsx` 提供 `retry()`（Next 16 已由 `unstable_retry` 穩定化）俾用戶重新 fetch + re-render segment。

## 3. 產品圖展示（next/image）

### 3.1 AVIF/WebP + `sizes` + 尺寸雙寫

**適用場景**：9 件選物嘅 hero／gallery 圖要輕、要清、唔縮 layout。

**點做**：`images.formats` 設 AVIF 優先、WebP fallback；`width`/`height` 或 `fill` 必填防 CLS；`fill` 或相對寬一定要 `sizes`，否則 browser 會攞最大 variant。

```ts
// next.config.ts
const nextConfig = {
  images: {
    formats: ['image/avif', 'image/webp'],
    deviceSizes: [640, 750, 828, 1080, 1200, 1920],
    imageSizes: [16, 32, 48, 64, 96, 128, 256],
  },
}
```

```tsx
<Image
  src={product.image}
  alt={product.name}
  fill
  sizes="(max-width: 768px) 100vw, 600px"
  placeholder="blur"
  blurDataURL={product.blurDataURL}
/>
```

**踩坑**：① 漏 `sizes` 會 download 過大 variant；② `width`/`height`（或用 `fill` + container aspect-ratio）先防到 layout shift。

### 3.2 LCP 圖：`priority` 已 deprecated（Next.js 16 起）

**適用場景**：首屏 hero／商品主圖係 LCP element，要最快開始 fetch。

**點做**：**Next.js 16 起 `priority` 已 deprecated**。官方建議**多數情況用 `loading="eager"` 或 `fetchPriority="high"`**，而唔係直接用 `preload`；`preload`（觸發 `<link rel="preload">` 插入 `<head>`）只喺「圖要喺 `<head>` 就被 preload、早過 `<body>` 發現」嘅 LCP 圖先用，而且唔可以同 `loading`／`fetchPriority` 一齊用。

```tsx
// 官方建議嘅 LCP 圖寫法（多數情況）
<Image
  src={hero.src}
  alt="THE HIRYU ROOM"
  fill
  loading="eager"          // 立即載入，唔使等 lazy
  fetchPriority="high"     // browser 優先 fetch
  sizes="(max-width: 768px) 100vw, 1200px"
/>
```

```tsx
// 特殊情況先用 preload（圖要喺 head 就被 preload，且冇用 loading/fetchPriority）
<Image src={hero.src} alt="hero" fill preload sizes="..." />
```

**踩坑**：① 唔好對多張圖都 `loading="eager"`／`preload`，會抵銷效益；② `preload` 同 `loading`／`fetchPriority` 互斥，唔好疊用；③ 有多張圖都可能係 LCP（視 viewport 而定）時唔好用 `preload`。

### 3.3 `placeholder="blur"` + `blurDataURL` pipeline

**適用場景**：圖片 load 完前用模糊佔位，改善 perceived performance、減低 CLS。

**點做**：static import（jpg/png/webp/avif）自動有 `blurDataURL`；remote/dynamic 圖要自己產 10×10 base64 存喺 product record。

```ts
// 上傳/建置時產 blur placeholder
import sharp from 'sharp'
export async function blurDataURL(buffer: Buffer) {
  const { data, info } = await sharp(buffer).resize(10).webp().toBuffer({ resolveWithObject: true })
  return `data:image/webp;base64,${data.toString('base64')}`
}
```

**踩坑**：① remote 圖唔會自動有 `blurDataURL`，要自己存；② 太細（≤10px）效果最好。

### 3.4 真產品相：拍攝 + 後製最佳實踐

**適用場景**：hiryu 由 mock data 換真 product 相，要有統一、可負擔嘅 catalog 質素。

**點做（拍）**：
- 軟光／擴散光：主光 **45°** 打向產品、稍高於視線，對面用 fill light（30–50% 功率）或白 reflector 柔化陰影。
- 白 seamless 背景、產品置中，產品佔 frame **80–90%**（mobile thumbnail 先睇到）。
- 用自然光就喺窗邊 + 薄紗／紙擴散；用人造光唔好混色溫；拍 RAW。

**點做（後製）**：
- 次序：white balance → exposure → 背景清潔／去背 → 去塵／刮痕 → 局部 sharpening（export 前）。
- **accurate & restrained**：改色溫、光暗、去瑕疵可以，唔好過度 retouch 到失真（誠實呈現）。
- 全 catalog 角度／打光／風格一致，export 按平台尺寸 + 高效壓縮（AVIF/WebP）。

**踩坑**：① 反光／亮面產品用更大光源、調角度避反光入鏡；② crop 唔好得 30% 佔比，mobile 會消失；③ 一致性比單張靚更重要（curated 店格調靠成套一致）。

## 4. 性能 Core Web Vitals

### 4.1 LCP：server 先 render LCP + 唔好包入慢 Suspense

**適用場景**：hero／商品主圖要喺 2.5s 內 paint。

**點做**：LCP element 放 Server Component、優先 render；LCP 圖 `preload` + 正確 `sizes`；用 SSG/ISR 做穩定頁、streaming SSR 做動態頁；`preload` 關鍵 asset。

```tsx
export default function RoomPage() {
  return (
    <>
      <HeroBanner />   {/* LCP 喺呢度，唔好包入 Suspense */}
      <Suspense fallback={<RoomSkeleton />}>
        <SlowRoomData />
      </Suspense>
    </>
  )
}
```

**踩坑**：① LCP 內容包喺慢 fetch 嘅 Suspense 內會拖慢 paint；② TTFB 目標 <100ms（PPR）、LCP <2.5s。

### 4.2 CLS：reserve space + 字體 metric override

**適用場景**：圖片、字體、streaming 內容唔好彈嚟彈去。

**點做**：next/image 明確尺寸或 `fill`+aspect-ratio；skeleton 尺寸要同最終內容一致；字體用 `next/font`（預設 `display: swap`）+ metric-compatible fallback。

```css
/* 減低 font swap 造成嘅 CLS */
@font-face {
  font-family: 'Source Han Serif Fallback';
  src: local('Songti SC'), local('Noto Serif CJK SC');
  size-adjust: 100%;
  ascent-override: 96%;
  descent-override: 20%;
}
```

**踩坑**：① CLS 目標 ≤0.1；② stream 入嚟嘅內容若 skeleton 高度唔同會跳，要對齊。

### 4.3 INP：縮 JS + 拆長 task

**適用場景**：2.5D 上樓視差／Framer Motion 動畫唔好令 click／scroll 卡頓（INP ≤200ms）。

**點做**：邏輯盡量放 Server Components，`'use client'` boundary 越低越好；`optimizePackageImports`、dynamic import、`@next/bundle-analyzer` 搵肥 bundle；defer third-party script；長 task 拆細。

```ts
// 拆 code splitting：互動組件 lazy load
const Room = dynamic(() => import('@/components/Room'), { ssr: false, loading: () => <RoomShell /> })
```

**踩坑**：① 大 main-thread task 直接傷害 responsiveness；② 動畫盡量用 `transform`/`opacity`（GPU），避 layout 屬性；③ 用 `requestIdleCallback`／`startTransition` 處理非緊急更新。

### 4.4 中文字體：subsetting + `display: swap` + self-host

**適用場景**：思源宋體等 CJK 字型成個 file 4MB，會拖爆 LCP。

**點做**：**CJK 唔好用 `subsets: ['latin']`**（中文字喺 latin subset 外）；self-host + 按 glyph coverage subsetting（可 4MB → ~300KB）；`display: 'swap'` 即時顯示 fallback 再換字型。

```tsx
import localFont from 'next/font/local'
const sourceHan = localFont({
  src: './SourceHanSerifSC-subset.woff2',
  display: 'swap',
  variable: '--font-source-han',
  adjustFontFallback: 'Times New Roman',  // next/font 自動計 fallback metric，減 CLS
})
```

**踩坑**：① 中文字型要靠自己 subsetting pipeline（如 subset-font / fonttools `pyftsubset`），`next/font` 嘅 `subsets` 幫唔到 CJK 覆蓋；② 系統 CJK fallback 先上、subsetted 字型後上，先顯示後換字；③ 拉丁文 + CJK 分開處理，唔好成個 CJK font 派俾所有用戶；④ `next/font` 嘅 `display` 預設 `'swap'`，用 `adjustFontFallback` 做 metric 對齊（唔使手寫 `size-adjust`）。

## 5. SEO

### 5.1 Metadata API（title/description/OG）+ `metadataBase`

**適用場景**：每個 product 頁要 dynamic title、description、canonical、OG。

**點做**：`metadata`（靜態）或 `generateMetadata`（dynamic，讀 params）；設 `metadataBase` 令相對 canonical／OG image URL 正確解析。

```ts
// app/products/[slug]/page.tsx
export async function generateMetadata({ params }): Promise<Metadata> {
  const p = await getProduct(params.slug)
  return {
    metadataBase: new URL('https://hiryu.co'),
    title: p.name,
    description: p.description,
    alternates: { canonical: `/products/${p.slug}` },
    openGraph: { title: p.name, description: p.description, images: [`/products/${p.slug}/opengraph-image`] },
  }
}
```

**踩坑**：① 冇 `metadataBase`，相對 URL 嘅 OG image／canonical 會解錯；② canonical 用絕對 URL。

### 5.2 JSON-LD：`<script type="application/ld+json">`（Product / Organization）

**適用場景**：Product schema 攞 rich results（價格、庫存、評分），Organization 做品牌。

**點做**：**JSON-LD 用 `<script>` tag 落，唔好用 Metadata API**；Organization/WebSite 放 root layout（site-wide），Product 放 product 頁；schema 內容要同頁面可見資料一致；JSON 要 escape `<` 做 `\u003c`。

```tsx
// app/layout.tsx — Organization（site-wide）
const org = { '@context': 'https://schema.org', '@type': 'Organization', name: 'HIRYU', url: 'https://hiryu.co', logo: 'https://hiryu.co/logo.png' }
;<script type="application/ld+json" dangerouslySetInnerHTML={{ __html: JSON.stringify(org).replace(/</g, '\\u003c') }} />
```

```tsx
// app/products/[slug]/page.tsx — Product
const productLd = {
  '@context': 'https://schema.org', '@type': 'Product',
  name: p.name, image: [p.image],
  offers: { '@type': 'Offer', price: p.price, priceCurrency: 'HKD', availability: p.stock > 0 ? 'https://schema.org/InStock' : 'https://schema.org/OutOfStock' },
}
;<script type="application/ld+json" dangerouslySetInnerHTML={{ __html: JSON.stringify(productLd).replace(/</g, '\\u003c') }} />
```

**踩坑**：① JSON-LD 唔經 Metadata API（佢唔支援 ld+json）；② schema 內容要同頁面 visible 資料一致，否則 Google 可能唔採用／判 mismatch；③ 用 Google Rich Results Test 驗證。

### 5.3 sitemap + opengraph-image

**適用場景**：9 件產品要自動 sitemap；分享時有靚 OG 圖。

**點做**：`app/sitemap.ts` 回傳 `MetadataRoute.Sitemap`；`app/opengraph-image.tsx` 用 `ImageResponse` 動態生 OG 圖（build/request time）。

```ts
// app/sitemap.ts
export default function sitemap(): MetadataRoute.Sitemap {
  return products.map(p => ({ url: `https://hiryu.co/products/${p.slug}`, lastModified: new Date(p.updatedAt) }))
}
```

// app/opengraph-image.tsx

## 6. Analytics / 轉化

### 6.1 精簡 funnel + 標準 ecommerce 事件

**適用場景**：9 件選物要知邊個位流失（view → add → checkout → pay）。

**點做**：用 Google 建議嘅最少事件集：`view_item` → `add_to_cart` → `begin_checkout` → `add_payment_info` → `purchase`；每個 event 帶足參數（product ID、price、quantity、cart value、order ID、payment type）。

```ts
// lib/analytics.ts — 統一埋點封裝（可接 GA4 / Plausible / PostHog）
export function track(event: string, params: Record<string, any>) {
  // window.dataLayer.push({ event, ...params })  // GA4
  // or analytics.track(event, params)           // 自選 provider
}
track('add_to_cart', { item_id: p.id, item_name: p.name, price: p.price, quantity: 1 })
track('purchase', { transaction_id: orderId, value: total, currency: 'HKD', items })
```

**踩坑**：① 每個 event 只 fire 一次（重複 event 會灌水轉化率）；② funnel 4–6 步就夠，第一步唔好太 broad。

### 6.2 收入關鍵 event 用 server-side / 付款確認

**適用場景**：ad blocker／iOS Safari 限制／script 失敗會漏掉 `purchase`，令數據失真。

**點做**：`purchase` 由 webhook（`checkout.session.completed`）或 server-side 確認後 fire，唔好淨靠 browser；定期同 payment processor 對數。

**踩坑**：① browser-only tracking 會被 ad blocker 擋；② 對唔上數 = 有 bug，先修 data quality 再落結論。

### 6.3 A/B 測試：單一主 metric + guardrail + 下游影響

**適用場景**：改 landing／CTA／商品頁／結帳 flow 前，要量到真正提升。

**點做**：一次只測一個 bottleneck；定義一個 primary metric + 一個 guardrail（防「提升一步、傷害收入／客單價」）；測完量下游影響（唔好只睇 click 數）。埋點要帶 experiment/variant id 先可以分組。

```ts
track('experiment_view', { experiment: 'hero-v2', variant: userInVariant('hero-v2') ? 'B' : 'A' })
```

**踩坑**：① 唔好只睇 step 完成率，要睇最終收入／轉化；② 先分段（device／channel／visitor type）先落手，平均數會呃人；③ 定性工具（heatmap／session replay）解釋「點解」流失。
